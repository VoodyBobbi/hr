# HR-ассистент ООО ПОЛАТИ


Вопросно-ответный AI-ассистент киборг (HR-менеджер по подбору персонала) для строительной компании
ПОЛАТИ. Отвечает кандидатам на вопросы по вакансиям и условиям работы строго на основе базы
знаний компании, помнит контекст диалога и помогает заполнить анкету кандидата.

Пайплайн: **данные (FAQ + база знаний) → RAG через FAISS → backend на FastAPI + GigaChat →
чат-виджет на сайте и Telegram-бот**.

За счёт супер автоматизации ответов на любые вопросы кандидатов ассистент снимает до 70–80% нагрузки
с рекрутёров и сокращает среднее время первого ответа кандидату, работая 24/7 без участия
человека.

## Возможности

- **Ответы только по базе знаний компании, экономно по токенам** — сначала поиск (готовые
  FAQ-ответы отдаются напрямую, без GigaChat; если не нашлось — отдельный поиск по базе знаний
  подмешивает в промпт GigaChat только несколько релевантных фактов, а не всю базу целиком) — не
  выдумывает факты (RAG-подход), не отвечает на вопросы не по теме трудоустройства (см.
  `system_prompt.md`).
- **Память диалога** — история переписки хранится по каждому пользователю, общение остаётся
  осмысленным.
- **Два канала** — чат-виджет на сайте и Telegram-бот, общая логика ответа.
- **Защита от спама и злоупотреблений на обоих каналах** — простой лимит по числу запросов в
  минуту с одного IP (только сайт, `slowapi`) плюс балльная система по паттернам поведения на
  обоих каналах (`backend/rate_limiting.py`, ключ — IP на сайте и `chat_id` в Telegram): повтор одного и того же сообщения, слишком частые
  сообщения, аномально длинный текст — каждый признак добавляет баллы, при достижении порога
  временная блокировка. Раньше у Telegram-канала не было вообще никакого ограничения.
- **Заполнение анкеты кандидата** — детерминированная стейт-машина (`backend/anketa.py`), без
  участия GigaChat: по одному полю, с проверкой формата каждого поля (`validators.py`) и заранее
  написанными дружелюбными вопросами/ошибками. Карточка кандидата в `candidates.csv` заводится
  только ПОСЛЕ явного согласия по 152-ФЗ — тот, кто просто задал вопрос о вакансиях и ушёл, не
  оставляет о себе записи в таблице персональных данных вообще. GigaChat не видит значения полей анкеты (включая
  паспорт, СНИЛС, ИНН) — только ведёт обычный FAQ-диалог и подаёт единственный управляющий сигнал
  (`START_ANKETA`), когда кандидат явно соглашается начать анкету.
- **Персональные данные — отдельно от кода в git и зашифрованы.** Анкеты и логи лежат в
  `candidates/` и `logs/` на верхнем уровне папки проекта (по умолчанию) — на виду, без лишних
  подпапок; история переписки — в `history/`. Все три добавлены в `.gitignore`: `git add
  .`/`git push` их никогда не подхватывают (см. раздел «Переменные окружения»). Файл анкет
  (`candidates.csv`) зашифрован целиком (Fernet); логи (`logs.csv`) и история переписки —
  построчно/по сообщениям (шифруются только поля с текстом, служебные колонки вроде даты и
  статуса остаются открытыми для удобного просмотра). Ключ шифрования один на все три —
  переменная окружения `ENCRYPTION_KEY`.
- **Удаление данных кандидата по запросу** — `python -m scripts.delete_candidate <ID>` стирает
  анкету, привязку сессии, историю переписки И соответствующие строки в логах (`logs.csv`) —
  полное удаление, без остатка персональных данных ни в одном файле.
- **Логирование** — все обращения пишутся в `logs/logs.csv` (источник, вопрос, ответ, время
  ответа, статус, комментарий, токены на вход/выход/всего/из кеша — см. `backend/logger.py`).
  Хранится `LOGS_RETENTION_DAYS` дней (по умолчанию 90, см. «Переменные окружения»), затем старые
  строки удаляются автоматически при каждом запуске.
- **Автоматическое обновление базы знаний** — при каждом запуске программа проверяет папку
  `data/`: если туда добавили/изменили файлы с вопросами-ответами или инструкциями (в любом из
  поддерживаемых форматов), векторный индекс пересобирается автоматически; если ничего не
  менялось — пересборка пропускается; если готового индекса ещё нет вообще — он собирается с
  нуля. Отдельно, без пересборки индекса, «на лету» подхватываются изменения промпта и
  структурированной базы знаний (см. «Как это работает» и «Обновление базы знаний»).

Анкеты кандидатов, логи и история переписки **не хранятся в git** — папки `candidates/`, `logs/`
и `history/` (все три создаются программой в корне проекта, см. «Переменные окружения») добавлены
в `.gitignore`. Это отдельно от кода намеренно: раньше похожая папка с candidates.csv
через `git add .` случайно попала в git и в публичный GitHub-репозиторий — теперь `git add
.`/`git push` никогда её не подхватывают, что бы в ней ни лежало.

## Как это работает

1. **Данные.** Частые вопросы лежат в `data/faqs.json` в формате `{"question": ..., "answer": ...}`.
   Справочная информация о компании, вакансиях и условиях — в тематических файлах
   `data/kb/`. Правила поведения ассистента — в `data/system_prompt.md`; фактов там
   больше нет, только правила. Можно
   добавить в `data/` дополнительные файлы: ещё один `.json` в том же формате `question/answer`,
   либо `.txt`/`.md` с текстом инструкций в свободной форме — весь текст такого файла целиком
   становится одним элементом базы знаний (см. «Обновление базы знаний» про то, как именно).
2. **Два раздельных индекса.** `build_index.py` при каждом запуске независимо проверяет два
   источника — FAQ (`data/faqs.json` плюс любые дополнительные `.json`/`.txt`/`.md` прямо в
   `data/`, кроме служебных файлов) и базу знаний (все файлы из `data/kb/`, каждая запись
   отдельным фрагментом, `backend/kb_chunker.py`). Если
   что-то изменилось с прошлого запуска — соответствующий источник превращается в вектора
   моделью `paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers) и сохраняется как
   отдельный FAISS-индекс (`faiss_index.bin` для FAQ, `kb_faiss_index.bin` для базы знаний,
   каждый со своими метаданными); если ничего не менялось — переиспользуется готовый индекс;
   изменение одного источника не трогает индекс другого (независимые хеши). Два раздельных
   индекса, а не один общий список результатов — у FAQ и базы знаний разное назначение (готовый
   ответ целиком против фактов для контекста), совместный top-k мог бы вытеснить более
   релевантный результат одного источника менее релевантным результатом другого.
3. **Запрос — сначала поиск, потом (если нужно) GigaChat.** При сообщении кандидата
   `assistant.py` векторизует вопрос и сначала ищет только в FAQ-индексе: если находится
   достаточно похожий вопрос — его готовый ответ отдаётся кандидату НАПРЯМУЮ, без обращения к
   GigaChat вообще (экономит и деньги, и время ответа). Если в FAQ ничего похожего не нашлось —
   отдельно ищутся релевантные факты в индексе базы знаний, они подмешиваются в системный
   промпт вместе с историей диалога, и только тогда вызывается **GigaChat** — с промптом,
   содержащим лишь несколько найденных фактов, а не всю базу знаний целиком.
4. **Анкета.** Когда кандидат соглашается заполнить анкету, GigaChat ставит единственный
   управляющий маркер `###START_ANKETA###` — он вырезается из ответа пользователю, а само
   заполнение (согласие 152-ФЗ, все 29 вопросов, подтверждение карточки, удаление по запросу)
   ведёт отдельная детерминированная логика (`backend/anketa.py`), без обращения к GigaChat —
   персональные данные кандидата (паспорт, СНИЛС, ИНН и остальное) в промпт не попадают вообще,
   пока анкета не будет завершена или отклонена, после чего диалог возвращается к GigaChat.
5. **Интерфейс.** `app.py` отдаёт сайт (`frontend/index.html`) и принимает запросы на `POST /chat`;
   `telegram_bot.py` использует то же ядро для Telegram.

## Требования

- Python 3.10+ (рекомендуется 3.11) — или Docker/Docker Compose, если запускаете в контейнере
- Доступ к GigaChat API (переменная `GIGACHAT_CREDENTIALS`)
- Токен Telegram-бота — только если нужен Telegram-канал (`TELEGRAM_BOT_TOKEN`)

## Переменные окружения

Скопируйте `.env.example` в `.env` и заполните (либо просто запустите `python setup.py` — он
сделает копию `.env` сам, см. «Установка и запуск» ниже):

```env
GIGACHAT_CREDENTIALS=ваш_ключ_авторизации_GigaChat
TELEGRAM_BOT_TOKEN=токен_вашего_бота   # опционально, только для Telegram

# Обязательно — ключ шифрования candidates.csv. Генерируется автоматически
# командой 'python setup.py' — вручную вписывать не нужно.
ENCRYPTION_KEY=

# Опционально — где на диске хранить анкеты/историю/логи.
# По умолчанию все три в корне проекта: candidates/, logs/, history/
# (ничего из этого не в git, см. .gitignore). Если задать HR_DATA_DIR —
# все три переедут в указанную папку вместо расположений по умолчанию.
# HR_DATA_DIR=/home/admin/hr-data
```

Файл `.env` не коммитится (см. `.gitignore`). `ENCRYPTION_KEY` — потеря этого значения означает
потерю доступа к данным в `candidates.csv`, храните его отдельно (например, в менеджере паролей).

## Установка и запуск

Приложение рассчитано на локальный запуск — на компьютере/сервере администратора, без облачного
хостинга. Персональные данные остаются на этой же машине (см. «Переменные окружения» выше).

```bash
# 1. Клонировать репозиторий и перейти в него
git clone https://github.com/VoodyBobbi/HR.git
cd HR

# 2. Создать и активировать виртуальное окружение
python3 -m venv venv
source venv/bin/activate        # Linux/macOS
# .\venv\Scripts\activate       # Windows

# 3. Скопировать .env.example в .env и заполнить GIGACHAT_CREDENTIALS,
#    ALLOWED_ORIGINS (свой домен сайта) — см. комментарии в самом .env.example
#    про остальные переменные (все опциональны, у каждой разумное значение
#    по умолчанию). Можно пропустить этот шаг — setup.py на шаге 4 сам
#    создаст .env из .env.example, если его ещё нет.

# 4. Поставить зависимости, сгенерировать ключ шифрования анкет, собрать индекс
#    и запустить сайт + Telegram-бота — всё одной командой
python start.py
```

`python start.py` делает то же, что раньше требовало двух отдельных команд подряд (`python
setup.py`, затем `python run_all.py`) — теперь достаточно одной. Обе команды по отдельности
никуда не делись и продолжают работать так же, как раньше — это может понадобиться, например,
чтобы доустановить зависимости после обновления `requirements.txt`, не перезапуская сам сервер:

- `python setup.py` — ставит зависимости из `requirements.txt`, и если ключ шифрования
  (`ENCRYPTION_KEY`) в `.env` ещё не задан — генерирует новый, сам записывает его в `.env` и
  печатает сообщение с этим ключом. Если ключ уже был задан раньше — не трогает его (иначе анкеты,
  зашифрованные старым ключом, стали бы нечитаемыми). Можно безопасно запускать повторно в любой
  момент.
- `python run_all.py` — без отдельных ручных шагов: проверяет, что ключ шифрования на месте (если
  нет — подскажет запустить `python setup.py`), создаёт папки для персональных данных (`candidates/`,
  `logs/`, `history/`, если их ещё нет), проверяет и при необходимости пересобирает
  векторный индекс из всего содержимого `data/` (если ничего не менялось с прошлого запуска —
  пересборка пропускается, это быстро), удаляет из логов строки старше `LOGS_RETENTION_DAYS` дней,
  запускает сайт и Telegram-бота.

Откройте <https://localhost:8000> (именно `https://`, не `http://` — см. ниже, раздел
«Локальный запуск с HTTPS», без этого чат не будет помнить диалог между сообщениями) — в правом
нижнем углу появится иконка чата. Анкеты появятся в `candidates/`, логи — в `logs/`, история
переписки — в `history/` (или всё вместе в папке из `HR_DATA_DIR`, если задали свою —
см. «Переменные окружения»).

Если нужен только сайт, без Telegram-бота — запустите `uvicorn backend.app:app --host 0.0.0.0
--port 8000` вместо `run_all.py` (индекс в этом случае пересоберите заранее один раз командой
`python -m backend.build_index`, автоматика из `run_all.py` в этом режиме не сработает).

### Локальный запуск с HTTPS

Сессия кандидата (`session_id`) хранится в cookie с флагом `Secure` (см. подробный комментарий у
`SESSION_COOKIE_NAME` в `backend/app.py`) — это осознанный выбор без исключений: браузер физически
не сохранит такую cookie по незашифрованному `http://`, поэтому **простой запуск по
`http://localhost:8000` не будет запоминать диалог между сообщениями** — каждое новое сообщение
будет создавать новую пустую анкету.

Самый быстрый способ получить HTTPS локально — самоподписанный сертификат через `mkcert`
(не требует настоящего домена, браузер будет доверять ему на вашем компьютере):

```bash
# 1. Установить mkcert (один раз)
#    Windows (через Chocolatey):  choco install mkcert
#    macOS (через Homebrew):      brew install mkcert
#    Linux:                       см. https://github.com/FiloSottile/mkcert#installation

# 2. Создать локальный доверенный корневой сертификат (один раз)
mkcert -install

# 3. Выпустить сертификат для localhost (в папке проекта)
mkcert localhost 127.0.0.1

# Это создаст два файла: localhost+1.pem (сертификат) и localhost+1-key.pem (ключ)

# 4. Запустить сайт с этим сертификатом вместо обычного run_all.py:
uvicorn backend.app:app --host 0.0.0.0 --port 8000 \
  --ssl-certfile localhost+1.pem --ssl-keyfile localhost+1-key.pem
```

Дальше открывайте <https://localhost:8000> — браузер покажет обычный замок в адресной строке
(не предупреждение о недоверенном сертификате), и cookie сессии будет сохраняться.

Обратите внимание: команда выше (`uvicorn ... --ssl-certfile ...`) заменяет `python run_all.py`
— она запускает только сайт, без Telegram-бота и без автоматической пересборки индекса/проверки
ключа. Для полноценной локальной разработки с HTTPS удобнее один раз выполнить `python setup.py`
и `python run_all.py` без HTTPS (это подготовит всё: зависимости, ключ, индекс), затем
останавливать процесс и перезапускать именно этой `uvicorn`-командой с сертификатом для
собственно тестирования через браузер.

### Запуск в Docker (тот же локальный компьютер)

```bash
docker compose up --build
```

Поднимет сайт на <http://localhost:8000> и, если задан `TELEGRAM_BOT_TOKEN`, Telegram-бота тоже —
оба процесса живут в одном контейнере (см. комментарий в `docker-compose.yml` про то, почему один
контейнер, а не несколько). Данные будут лежать в папке `./hr-data` рядом с `docker-compose.yml`
(путь настраивается в самом файле). `.env` должен быть заполнен ЗАРАНЕЕ, включая уже
сгенерированный `ENCRYPTION_KEY` — Docker-режим сам зависимости не ставит и ключ не генерирует
(`python setup.py` рассчитан на запуск вне контейнера, до `docker compose up`; если ключа в `.env`
нет, `start.sh` выведет об этом сообщение и не запустится). Compose передаёт `.env` в контейнер
автоматически. Пересборка индекса и очистка логов при старте происходят автоматически, как и при
локальном запуске (см. `start.sh`).

В `docker-compose.yml` задано `SESSION_COOKIE_SECURE=false`. Контейнер поднимает сайт по обычному
`http://localhost:8000`, а cookie с флагом `Secure` браузер по такому адресу не сохраняет — без
этой строки диалог не помнился бы между сообщениями, и каждое сообщение начинало бы новую анкету.
Это только для локальной проверки: если поднимаете compose на сервере, доступном по сети, уберите
строку и поставьте перед контейнером обратный прокси с HTTPS.

## API

| Метод | Путь      | Описание                                                        |
|-------|-----------|----------------------------------------------------------------|
| GET   | `/`       | Главная страница сайта с чат-виджетом                           |
| POST  | `/chat`   | Отправить сообщение ассистенту                                   |
| GET   | `/health` | Проверка работоспособности сервиса (`{"status": "ok"}`)         |

Пример запроса к `/chat`:

```json
{
  "message": "Какие у вас есть вакансии?"
}
```

Ответ:

```json
{
  "answer": "...",
  "context": [ ... ],
  "session_id": "..."
}
```

`top_k` (сколько похожих вопросов искать в базе FAQ) зашит константой в `backend/app.py` и не
принимается от клиента вообще — раньше это было полем запроса, что позволяло прислать
искусственно завышенное значение и заставить сервер делать избыточную работу на каждое
сообщение.

`session_id` в ответе — только для совместимости формата; сервер сам выдаёт и отслеживает
сессию через `HttpOnly`+`Secure` cookie (см. `backend/app.py`), клиент ничего не должен
передавать в теле запроса, чтобы сохранялась память диалога — браузер прикладывает cookie
автоматически (нужен `credentials: "include"` в `fetch()`, уже сделано в `frontend/index.html`).
Раньше `session_id` принимался из тела запроса — это позволяло подставить чужой идентификатор и
получить доступ к чужой анкете; теперь тело запроса на это никак не влияет.

**Виджет на другом домене.** По умолчанию cookie выдаётся с `SameSite=Lax` — это правильно, пока
страница с виджетом и сервер бота находятся на одном домене. Если встроить виджет на сайт
компании, а бота держать на отдельном домене или поддомене, запрос к `/chat` станет cross-site, и
браузер cookie с `Lax` к нему не приложит: диалог перестанет помниться, каждое сообщение начнёт
новую анкету. Для такого размещения поставьте в `.env` `SESSION_COOKIE_SAMESITE=none` — `Secure`
при этом включается принудительно, этого требует сам браузер.

**Важно про HTTPS даже локально:** флаг `Secure` у cookie означает, что браузер не сохранит её
на обычном `http://localhost` без HTTPS — каждое сообщение будет создавать новую сессию вместо
того, чтобы продолжать диалог. Это осознанный выбор без исключений (см. `backend/app.py`,
комментарий у `SESSION_COOKIE_NAME`) — для локальной разработки нужен HTTPS даже на своём
компьютере, см. раздел «Локальный запуск с HTTPS» ниже.

## Удаление данных кандидата (152-ФЗ)

Есть два независимых способа — оба удаляют одно и то же (строку из `candidates.csv`, привязку
сессии в `candidate_sessions.json`, файл(ы) истории переписки И строки в `logs.csv`,
относящиеся к этому кандидату):

**1. Сам кандидат — прямо в диалоге с ботом**, в любой момент заполнения анкеты (не через
обычный FAQ-диалог с GigaChat — если анкета ещё не начата, это просто обычный вопрос кандидату,
не команда). Кандидат пишет что-то вроде «удали мои данные» — бот переспрашивает подтверждение
и удаляет только после явного повторного «да, удали» (распознавание по ключевым словам,
`backend/anketa.py`, без участия GigaChat — как и весь остальной ход анкеты, см. раздел «Как это
работает»). Дальнейшие сообщения от этого же кандидата создадут новую, пустую анкету — это
ожидаемо, старых данных больше не существует.

**2. HR вручную, по номеру ID:**

```bash
python -m scripts.delete_candidate <ID_кандидата>
```

ID — это номер колонки в `candidates.csv` (см. поле «ID кандидата» в карточке), не телефон и не
ФИО. Скрипт спросит подтверждение и удалит те же данные, что и способ 1.

Строки в `logs/logs.csv`, относящиеся к этому кандидату, удаляются обоими способами вместе с
остальными данными (`backend/logger.py`, `delete_logs_for_session`) — иначе текст переписки
остался бы в логе уже после удаления самой переписки, и право на удаление по ст. 21 152-ФЗ
выполнялось бы не полностью. Независимо от этого весь лог целиком ограничен по сроку хранения
переменной `LOGS_RETENTION_DAYS` в `.env` (по умолчанию 90 дней) — это отдельный механизм, не
привязанный к конкретному кандидату (`purge_old_logs`).

## Уведомления HR о новых заявках

Когда кандидат полностью заполняет анкету и подтверждает её (см. раздел «Как это работает» —
подтверждение обрабатывает `backend/anketa.py`, не GigaChat), бот может отправить короткое
уведомление в отдельную Telegram-группу HR — без каких-либо персональных данных вообще, включая
телефон (только ФИО, вакансия, источник обращения, ID кандидата в таблице и отметка об
ознакомлении с 152-ФЗ; полная анкета — паспорт, СНИЛС, ИНН, телефон и всё остальное — остаётся
только в зашифрованном `candidates.csv`, открыть который может только тот, у кого есть
`ENCRYPTION_KEY`, а не любой участник группового чата).

Функция полностью опциональна: если переменные ниже не заданы в `.env`, бот просто не пытается
никого уведомлять и продолжает работать как обычно.

Отправляет уведомления **тот же самый бот**, что общается с кандидатами (тот же
`TELEGRAM_BOT_TOKEN` из `.env`) — заводить для этого отдельного второго бота не нужно.

**Как настроить (один раз):**

1. Создайте в Telegram отдельную группу для заявок HR (или используйте существующую).
2. Добавьте в эту группу своего бота — как обычного участника, через «Добавить участника» → найти
   бота по его username (тот, что вы указывали при создании бота через @BotFather).
3. Узнайте правильный `chat_id` этой группы — см. пошагово ниже. **Число из ссылки веб-версии
   Telegram (`web.telegram.org/k/...#-XXXXXXXXXX`) для этого, как правило, НЕ подходит напрямую**
   — это внутренний идентификатор клиентского приложения (Telegram Web), а не тот `chat_id`,
   который понимает Bot API; используются разные системы нумерации.
4. Добавьте в `.env` строку `TELEGRAM_HR_GROUP_CHAT_ID=` с полученным числом, включая знак минуса
   в начале (см. `.env.example`).
5. Перезапустите бота (`python run_all.py`).

**Как узнать правильный `chat_id` (единственный надёжный способ):**

1. Отправьте в HR-группу (той, куда добавили бота) любое сообщение — например, просто «привет» —
   от своего личного аккаунта, не от бота.
2. Откройте в браузере (замените `<ТОКЕН>` на значение `TELEGRAM_BOT_TOKEN` из вашего `.env`):
   ```
   https://api.telegram.org/bot<ТОКЕН>/getUpdates
   ```
3. В открывшемся тексте найдите `"chat":{"id":` — рядом будет число, обычно отрицательное и
   начинающееся на `-100` для групп (например `-1001234567890`). Это и есть нужное значение.
4. Если результат пустой (`"result":[]`) — значит Telegram ещё не переслал боту то тестовое
   сообщение из шага 1; подождите несколько секунд и обновите страницу, либо отправьте в группу
   ещё одно сообщение и попробуйте снова.

**Если нужно поменять группу или создать новую** — тот же порядок действий сначала (шаги 1-5
выше) с новой группой; специальный бот-администратор для *этого* не нужен — обычных прав
администратора Telegram-группы (которые есть у создателя группы) достаточно, чтобы добавить в
неё бота и получить `chat_id` через `getUpdates`. Отдельный бот-администратор понадобился бы,
только если вы захотите, чтобы сам бот-ассистент умел управлять группой программно (менять
название, права участников и т.п.) — сейчас проект этого не делает, он только отправляет
сообщения в уже настроенную вами группу.

Если после настройки уведомления всё равно не приходят — проверьте логи запуска сервера: при
ошибке отправки (неверный `chat_id`, бот не в группе, токен истёк) в консоль печатается
`[notifications] Telegram Bot API вернул ...` с точным кодом ошибки от Telegram.

## Обновление базы знаний

При каждом запуске (`python run_all.py` или `docker compose up`) программа сама проверяет папку
`data/` целиком и решает, что делать, без ручных команд:

- **Готового индекса нет вообще** (первый запуск, либо индекс удалили) — собирается с нуля.
- **Что-то в `data/` изменилось** с прошлого запуска (файл отредактировали, добавили новый,
  удалили старый) — индекс пересобирается автоматически.
- **Ничего не менялось** — пересборка пропускается, старт быстрый.

Как добавить новые вопросы-ответы или инструкции — положите файл в `data/` в одном из форматов:

- **`.json`** (например, ещё один файл рядом с `faqs.json`, с любым именем) — в формате
  `[{"question": "...", "answer": "..."}, ...]`, тот же, что и в `faqs.json`. Каждая пара
  становится отдельным элементом базы для векторного поиска.
- **`.txt` или `.md`** — текст инструкции в свободной форме, без структуры вопрос/ответ. Весь
  файл целиком становится ОДНИМ элементом базы: как «вопрос» используется имя файла, как «ответ»
  — содержимое файла без изменений. Модель не разбивает и не переформулирует такой файл на
  несколько вопросов — если нужны отдельные вопросы с отдельными ответами, используйте формат
  `.json` выше.
- Файлы в других форматах (например, `.docx`, `.pdf`, изображения) при сборке индекса пропускаются
  с предупреждением в консоли — их нужно предварительно сохранить как `.txt`/`.md`/`.json`.

Принудительно пересобрать индекс в любой момент, даже если ничего не менялось — `python -m
backend.build_index --force`.

Отдельно про `data/system_prompt.md`: его изменения пересборки НЕ требуют вообще — этот файл
подхватывается на лету при следующем запросе к уже запущенному серверу, без перезапуска и без
ожидания пересборки эмбеддингов (это неструктурированный текст инструкции для GigaChat, не
источник фактов для векторного поиска).

Папка `data/kb/`, в отличие от `system_prompt.md`, ТРЕБУЕТ пересборки при изменении — у неё
свой собственный, независимый от FAQ индекс (`kb_faiss_index.bin`). Каждая запись из
тематических файлов становится отдельным фрагментом (`backend/kb_chunker.py`) и индексируется
отдельно, чтобы искать релевантные факты по вопросу кандидата, а не подавать всю базу знаний в
промпт целиком. Пересборка происходит автоматически при следующем запуске, независимо от
FAQ-индекса — изменение одного источника не трогает индекс другого.

Битый JSON в одном тематическом файле не роняет сборку: файл пропускается с предупреждением в
консоли, остальные индексируются как обычно.

## Как устроена база знаний и почему это экономит токены

Информация о компании разложена по двум разным механизмам, и разница между
ними принципиальная.

**`data/faqs.json` — готовые ответы.** Если вопрос кандидата достаточно близок
к одному из записанных вопросов, ответ уходит ему **напрямую, без обращения к
GigaChat**. Это самый дешёвый путь: ноль токенов, мгновенный ответ. Сюда стоит
складывать всё, что спрашивают часто и на что есть один правильный ответ.

**`data/kb/*.json` — факты для модели.** Когда готового ответа нет, отдельный
поиск находит несколько релевантных фактов и подмешивает **только их** в промпт
GigaChat. Модель формулирует ответ на их основе.

Формат записи в базе знаний:

```json
{
  "id": "med.vision",
  "title": "Требования к зрению",
  "keywords": ["зрение", "очки", "линзы", "диоптрии", "плохо вижу"],
  "text": "Зрение должно быть в диапазоне от -2 до +2..."
}
```

`keywords` — это формулировки, которыми кандидат реально задаёт вопрос. Они
участвуют в поиске, но **не уходят в промпт**: модели они не нужны и только
тратили бы токены. Раньше заголовком фрагмента был путь в дереве вида
`vacancies.montazhnik.salary`, и вопрос «сколько платят монтажнику» почти не
пересекался с этим текстом — теперь пересекается и заголовком, и синонимами.

**Что даёт разделение.** Раньше все факты о компании лежали прямо в
`system_prompt.md`, и полный перечень условий, зарплат, нормативов и адресов
уходил в GigaChat при каждом сообщении, включая «здравствуйте». Теперь
неизменная часть промпта содержит только правила поведения, а конкретика
приезжает адресно под заданный вопрос:

| | Было | Стало |
|---|---|---|
| Правила поведения | ~6600 токенов | ~2600 токенов |
| Факты | вся база сразу | до ~950 токенов по теме |
| **Промпт на один запрос** | **~6900 токенов** | **~3100 токенов** |

Экономия около 55% на каждом обращении к модели — и это сверх того, что часть
вопросов вообще не доходит до GigaChat, получая готовый ответ из `faqs.json`.

### Как добавить или изменить информацию

Частый вопрос с одним правильным ответом — в `data/faqs.json`. Справочный факт,
который модель должна знать, — в подходящий файл `data/kb/`. Новая тема — новый
файл в `data/kb/`, в коде менять ничего не нужно, он подхватится сам.

После правки достаточно перезапустить проект: индекс пересобирается
автоматически, когда содержимое `data/` изменилось.

## Калибровка порогов поиска

Поиск отсекает нерелевантные результаты по порогу **косинусной близости** —
числу от 0 до 1, где больше значит похожее. 0.45 — «примерно об одном», 0.75 —
«почти то же самое».

Два независимых порога в `.env`, потому что у поисков разная цена ошибки:

- **`FAQ_MIN_SIMILARITY`** (по умолчанию `0.62`) — готовый ответ уходит
  кандидату напрямую, поэтому порог строгий: промах здесь виден как уверенный
  ответ не на тот вопрос. Бот слишком часто «не знает» того, что есть в FAQ —
  снизьте до `0.55`. Отвечает не по делу — поднимите до `0.70`.
- **`KB_MIN_SIMILARITY`** (по умолчанию `0.35`) — факты только подмешиваются в
  промпт, решение всё равно принимает GigaChat, поэтому лишний факт дешевле
  пропущенного.

Калибруйте по `logs/logs.csv`: строки, где ответ пришёл напрямую из FAQ,
помечены источником `faq_direct`.

### Две тонкости, на которых легко ошибиться

**Нормализация векторов.** У `sentence-transformers` параметр
`normalize_embeddings` по умолчанию равен `False`. Без нормализации длины
векторов этой модели заметно больше единицы, и любой порог, выставленный «на
глаз», оказывается бессмысленным. Нормализация включена в
`backend/build_index.py` и `backend/assistant.py`, и включать её нужно
**в обоих местах сразу** — индекс и запрос обязаны строиться одинаково.

**Тип индекса.** Используется `faiss.IndexFlatIP` (скалярное произведение). На
нормализованных векторах оно равно косинусной близости, поэтому поиск сразу
возвращает читаемое число. Прежний `IndexFlatL2` возвращал **квадрат**
евклидова расстояния в диапазоне 0–4, где меньше значит похожее — порог в таких
единицах невозможно осмыслить, и именно поэтому исходное значение было
выставлено неверно.

**Если меняете модель или способ векторизации** — поднимите `EMBEDDING_VERSION`
в `backend/build_index.py`. Пересборка индекса запускается по хешу файлов
`data/`, и без смены версии хеш совпал бы со старым, пересборка была бы
пропущена, а запросы искались бы по индексу, построенному по другим правилам.

## Постоянная работа на компьютере администратора

Проект больше не рассчитан на облачный хостинг (Render и т.п.) — он работает локально, на
компьютере или сервере, который контролирует администратор, а персональные данные остаются на
этой же машине. Чтобы сайт не отключался при закрытии терминала и поднимался заново после
перезагрузки компьютера, выберите один из вариантов:

- **Docker Compose** (проще всего) — `docker compose up -d --build`. В `docker-compose.yml` уже
  указано `restart: unless-stopped` — контейнер перезапустится сам после перезагрузки машины,
  пока Docker сам настроен на автозапуск.
- **systemd** (Linux, без Docker) — создайте юнит, который выполняет
  `uvicorn backend.app:app --host 0.0.0.0 --port 8000` из виртуального окружения проекта, и
  включите `systemctl enable`.
- **Планировщик заданий / NSSM** (Windows, без Docker) — запустите ту же команду uvicorn как
  задачу при входе в систему или как службу через NSSM.

Во всех трёх случаях `.env` должен быть на месте до запуска, включая уже сгенерированный
`ENCRYPTION_KEY` (получить его — `python setup.py`, см. «Установка и запуск») — без
`GIGACHAT_CREDENTIALS` и `ENCRYPTION_KEY` приложение не стартует.
